# 국제화 및 번역 기준

## 문서의 목적

이 문서는 ghostyak.com의 국제화 구현과 번역 작업에 적용하는 기준이다. 현재 사이트는 한국어만 공개하며, 이 문서에 적힌 구조는 국제화 구현의 목표 상태를 설명한다.

가장 중요한 원칙은 다음과 같다.

> **한국어 콘텐츠가 유일한 원문(source of truth)이다. 모든 번역은 확정된 한국어 콘텐츠의 의미, 정보 구조와 행동을 기준으로 작성한다.**

번역 언어에서 한국어에 없는 기능, 약속, 가격, 정책 또는 마케팅 표현을 독자적으로 추가하지 않는다. 번역을 먼저 수정해야 할 이유가 생기면 한국어 원문을 먼저 고친 뒤 같은 변경을 번역에 반영한다.

## 적용 범위

이 기준은 다음 공개 콘텐츠 전체에 적용한다.

- 헤더, 푸터, 버튼, 알림과 접근성 이름
- 홈페이지와 제품 페이지의 제목, 설명과 기능 소개
- 다운로드 안내, 버전과 시스템 요구사항
- 페이지 제목, 설명, Open Graph와 구조화 데이터
- Markdown 블로그의 frontmatter와 본문
- 이미지 대체 텍스트와 이미지 안에 포함된 문구
- 날짜, 숫자, 파일 크기와 기타 지역별 표시 형식

제품 버전, 설치 파일 URL, 이미지 파일과 기능 식별자처럼 언어와 무관한 값은 번역하지 않고 모든 언어가 같은 데이터를 공유한다.

## 용어

- **원문**: GhostYak이 직접 작성하고 승인한 한국어 콘텐츠
- **로케일(locale)**: 언어와 지역별 표시 규칙을 나타내는 식별자
- **번역 사전(dictionary)**: 동일한 키에 대해 언어별 UI 문구를 제공하는 데이터
- **번역 키**: 코드와 번역 사전 사이의 안정적인 의미 식별자
- **원문 리비전**: 번역이 어떤 한국어 원문 버전을 기준으로 작성되었는지 나타내는 값
- **완료된 로케일**: 필수 경로, 메타데이터와 접근성 문구까지 검수된 언어

## 로케일과 공개 URL

### 기본 언어

- 기본 언어는 한국어(`ko-KR`)다.
- 한국어 대표 URL에는 언어 접두사를 붙이지 않는다.
- `/`는 언제나 한국어 홈페이지이며 브라우저 언어에 따라 다른 언어로 자동 이동시키지 않는다.
- `/ko`와 `/ko/...`가 들어오면 접두사가 없는 한국어 대표 URL로 영구 리디렉션한다.

### 번역 언어

번역 언어에는 짧고 안정적인 소문자 로케일 접두사를 사용한다.

| 콘텐츠 | 한국어 대표 URL | 번역 URL 예시 |
| --- | --- | --- |
| 홈페이지 | `/` | `/en` |
| Boxes | `/product/boxes` | `/en/product/boxes` |
| 다운로드 | `/product/boxes/download` | `/en/product/boxes/download` |
| 블로그 목록 | `/blog` | `/en/blog` |
| 블로그 글 | `/blog/{slug}` | `/en/blog/{localizedSlug}` |

지원 로케일 목록은 한 개의 로케일 레지스트리에서 관리한다. 새 언어는 필수 화면을 모두 번역하고 검수한 뒤 레지스트리에 추가한다. 일부 화면만 번역된 언어를 공개 지원 목록에 넣지 않는다.

### 언어 선택

- 헤더의 언어 선택 메뉴로 사용자가 직접 언어를 바꾼다.
- 언어를 바꾸면 가능한 경우 현재 콘텐츠와 대응하는 번역 경로로 이동한다.
- 대응 번역이 없는 블로그 글에서는 해당 언어를 선택 불가능하게 표시하거나 그 언어의 블로그 목록으로 이동한다.
- 브라우저 `Accept-Language`는 언어 제안에 사용할 수 있지만 `/`의 자동 리디렉션 근거로 사용하지 않는다.
- 검색엔진과 사용자가 같은 URL에서 항상 같은 언어를 받아야 한다.

## 목표 코드 구조

국제화 구현 시 다음 역할을 분리한다.

```text
src/i18n/
├── locales.ts                 지원 로케일과 HTML·Open Graph 로케일
├── get-dictionary.ts          Server Component 전용 사전 로더
└── dictionaries/
    ├── ko.ts                  유일한 UI 원문
    ├── en.ts                  한국어 원문의 번역
    └── ...

content/blog/
├── ko/                        블로그 원문
│   └── hello-world.md
├── en/                        대응 번역
│   └── hello-world.md
└── ...
```

구현 세부 원칙은 다음과 같다.

- 한국어 사전의 키 구조를 다른 언어 사전의 TypeScript 타입 기준으로 사용한다.
- 지원 로케일의 필수 키가 없으면 빌드나 검증 단계에서 실패시킨다.
- 지원 중인 번역 화면에서 누락된 문구를 한국어로 조용히 대체하지 않는다.
- 번역 사전은 서버에서 동적으로 불러오며 전체 사전을 Client Component 번들에 포함하지 않는다.
- Client Component에는 현재 화면에서 필요한 번역 문자열만 props로 전달한다.
- 경로, 버전, 다운로드 URL과 이미지처럼 번역 대상이 아닌 데이터는 `src/data/`에서 공유한다.
- 현재 `src/data/products.ts`에 있는 한국어 설명과 기능 문구는 국제화 구현 시 한국어 사전으로 이동한다.
- 페이지와 공통 컴포넌트에 표시용 한국어 문자열을 직접 작성하지 않는다. 한국어도 사전을 통해 읽는다.
- App Router의 동적 로케일 경로와 `generateStaticParams`를 사용해 지원 언어를 정적으로 생성한다.
- 알 수 없는 로케일은 다른 언어로 추측해 보여주지 않고 404를 반환한다.

외부 국제화 라이브러리는 필요한 기능이 Next.js의 동적 경로와 서버 사전 로딩만으로 해결되지 않을 때만 도입한다. 도입 전 번들 크기, Server Component 지원, 타입 안전성과 유지보수 상태를 비교한다.

## 번역 키 작성 기준

- 키는 화면 위치가 아니라 의미를 나타낸다. 예: `boxes.download.action`, `blog.readMore`.
- 같은 한국어 문구라도 문맥이나 목적이 다르면 별도 키를 사용한다.
- 문장을 단어 조각으로 나누어 조합하지 않는다. 언어마다 어순이 다르므로 완전한 문장을 번역 단위로 둔다.
- 변수는 이름이 분명한 placeholder로 전달한다. 예: `{version}`, `{seconds}`.
- 복수형이나 성 구분이 필요한 언어를 문자열 연결로 처리하지 않는다.
- 접근성 이름, 오류, 빈 상태와 메타데이터도 일반 화면 문구와 같은 수준으로 키를 관리한다.
- 삭제된 기능의 번역 키는 참조 여부를 확인한 뒤 모든 사전에서 함께 제거한다.

## 번역 작성 기준

### 의미와 문체

- 한국어 원문의 사실, 범위와 행동을 정확히 유지한다.
- 단어 대 단어 번역보다 대상 언어에서 자연스럽고 명확한 문장을 우선한다.
- 원문보다 과장된 최상급 표현, 보장 또는 기능 약속을 추가하지 않는다.
- 제목은 짧고 직접적으로, 본문은 친절하지만 장황하지 않게 쓴다.
- 버튼은 사용자가 실행할 행동이 분명한 동사형 표현을 사용한다.
- 한 화면 안에서는 같은 개념에 같은 용어를 사용한다.
- 번역자 주석이나 미확정 표현을 공개 문자열에 남기지 않는다.

### 고정 표기

다음 명칭은 원칙적으로 번역하지 않는다.

| 원문 | 표기 원칙 |
| --- | --- |
| GhostYak | 브랜드 표기 그대로 사용 |
| Boxes | 제품명 표기 그대로 사용 |
| Windows 10/11 | Microsoft 제품 표기 유지 |
| Microsoft Edge WebView2 Runtime | 공식 제품명 유지 |
| GitHub Releases | 서비스 고유명사 유지 |

“box”가 일반적인 UI 개념을 뜻할 때는 대상 언어의 자연스러운 용어로 번역할 수 있지만 제품명 **Boxes**는 번역하지 않는다. 새로운 핵심 용어가 생기면 이 표에 먼저 추가한다.

## UI 콘텐츠 작업 순서

모든 기능과 문구 변경은 다음 순서를 따른다.

1. 한국어 화면에서 기능, 정보 구조와 문구를 작성한다.
2. 한국어 화면의 디자인, 접근성, 링크와 메타데이터를 검수한다.
3. 한국어 원문을 확정하고 번역 키 또는 원문 리비전을 갱신한다.
4. 각 지원 언어를 한국어 원문에서 번역한다.
5. 누락 키, 변수, 링크와 메타데이터를 자동 검증한다.
6. 원어민 수준의 언어 검수와 실제 화면 검수를 진행한다.
7. 필수 경로가 모두 완료된 로케일만 배포한다.

한국어 원문이 바뀌면 영향받는 번역을 “검수 필요” 상태로 되돌린다. 오탈자처럼 의미가 바뀌지 않는 수정인지, 기능 범위나 행동이 바뀌는 수정인지 구분해 기록한다.

## Markdown 블로그 번역

### 원문과 번역 연결

- 한국어 글은 `content/blog/ko/`에 두며 항상 원문이다.
- 번역 글은 `content/blog/{locale}/`에 둔다.
- 모든 언어의 대응 글은 동일한 `translationKey`를 사용한다.
- URL slug는 검색과 독자를 위해 언어별로 자연스럽게 작성할 수 있다.
- 한국어 글이 없는 번역 글은 만들지 않는다.
- 글 목록에는 해당 로케일로 완료된 글만 노출한다.

목표 frontmatter 형식은 다음과 같다.

```md
---
title: "글 제목"
description: "목록과 검색 메타데이터에 사용할 설명"
publishedAt: "2026-08-29"
translationKey: "hello-world"
sourceRevision: 1
---
```

번역 글은 `sourceRevision` 대신 또는 함께 `translatedFromRevision`을 기록한다. 한국어 글의 `sourceRevision`과 값이 다르면 빌드 검증 또는 콘텐츠 검사에서 오래된 번역으로 보고한다.

### 날짜와 공개 정책

- `publishedAt`은 원문의 최초 공개일을 유지한다.
- 번역이 나중에 추가되어도 원문을 새 글처럼 보이게 하지 않는다.
- 내용이 실질적으로 바뀌면 `updatedAt`을 모든 관련 언어에 반영한다.
- 번역이 없는 글에서 자동 기계 번역 결과를 즉석으로 노출하지 않는다.

## SEO와 메타데이터

- 각 언어 페이지는 자신의 URL을 canonical로 사용한다.
- 대응 페이지끼리 `hreflang` alternates를 연결한다.
- `x-default`는 접두사가 없는 한국어 대표 URL을 가리킨다.
- `<html lang>`에는 현재 로케일의 올바른 BCP 47 언어 태그를 설정한다.
- Open Graph `locale`과 대체 로케일을 언어별로 설정한다.
- 제목, 설명, 이미지 대체 텍스트와 JSON-LD의 설명 필드는 모두 번역한다.
- 제품명, 버전, 가격과 다운로드 URL 같은 사실 데이터는 언어별로 달라지지 않게 공유한다.
- sitemap에는 번역과 검수가 완료된 공개 URL만 포함한다.
- 다운로드 안내 페이지의 검색 제외 정책은 모든 언어에 동일하게 적용한다.

## 지역별 형식

- 날짜, 숫자와 단위는 `Intl.DateTimeFormat`, `Intl.NumberFormat` 등 표준 국제화 API로 표시한다.
- 날짜 문자열을 번역 사전에 완성된 문장으로 저장하지 않는다.
- 파일 크기, 버전과 운영체제 표기는 의미는 공유하되 순서와 구분 문자는 언어별 문장 구조에 맞춘다.
- 통화가 도입되면 가격의 원본 값과 통화 코드는 공유하고 표시만 로케일에 맞게 포맷한다.
- 시간대가 중요한 콘텐츠는 원본 시간대와 표시 시간대를 명시한다.

## 이미지와 시각 콘텐츠

- 제품 스크린샷처럼 문구가 없는 이미지는 모든 언어가 공유한다.
- 이미지 대체 텍스트는 언어별 사전에서 번역한다.
- 이미지 안에 문구가 들어가면 언어별 이미지가 필요한지 먼저 검토한다.
- 언어별 이미지가 필요하면 동일한 이미지 식별자 아래 로케일별 경로를 관리한다.
- 텍스트가 포함된 하나의 이미지를 모든 언어에 재사용해 번역되지 않은 UI가 노출되지 않게 한다.

## 레이아웃과 접근성 검수

번역 완료는 문자열 파일 작성만을 의미하지 않는다. 각 로케일에서 다음을 확인한다.

- 320px, 768px와 데스크톱 화면에서 가로 스크롤이 생기지 않는다.
- 긴 제목과 버튼이 잘리거나 겹치지 않는다.
- 한국어 길이를 기준으로 고정 너비를 만들지 않는다.
- 제목 계층, 랜드마크와 포커스 순서가 한국어 화면과 같다.
- `aria-label`, 이미지 대체 텍스트와 상태 알림이 현재 언어로 제공된다.
- 회전 화면의 재생·정지와 화면 선택 이름이 현재 언어로 제공된다.
- 언어 선택 메뉴는 현재 언어를 표시하고 키보드로 사용할 수 있다.
- 언어를 바꾸어도 사용자의 현재 콘텐츠 맥락이 가능한 한 유지된다.
- 지원하는 글꼴이 해당 언어의 문자와 강조 굵기를 올바르게 표시한다.

## 자동 검증 기준

국제화 구현과 함께 다음 검사를 마련한다.

- 지원 로케일마다 한국어 사전과 동일한 필수 키를 갖는지 확인
- placeholder 이름과 개수가 한국어 원문과 일치하는지 확인
- 번역 사전에 빈 문자열이나 임시 표식이 없는지 확인
- 공개 로케일의 필수 페이지가 모두 정적으로 생성되는지 확인
- 블로그 번역이 유효한 한국어 `translationKey`와 원문 리비전을 가리키는지 확인
- canonical, `hreflang`, `<html lang>`과 sitemap 관계 확인
- 코드에 새 표시용 하드코딩 문자열이 추가되지 않았는지 검토
- `npm run lint`와 `npm run build` 통과

자동 검사는 언어의 자연스러움을 보장하지 않는다. 번역 언어별 최종 문장 검수와 화면 검수는 별도로 진행한다.

## 새 언어 추가 완료 조건

새 로케일은 다음 조건을 모두 만족해야 지원 언어로 공개한다.

- [ ] 로케일 코드, 표시 이름, HTML 언어와 Open Graph 로케일 등록
- [ ] 공통 UI와 모든 필수 페이지 번역
- [ ] Boxes 제품 및 다운로드 안내 번역
- [ ] 페이지 메타데이터, JSON-LD와 이미지 대체 텍스트 번역
- [ ] 공개 대상으로 정한 블로그 글 번역 및 원문 리비전 확인
- [ ] 언어 선택과 대응 경로 이동 확인
- [ ] canonical, `hreflang`과 sitemap 확인
- [ ] 모바일·데스크톱 레이아웃 확인
- [ ] 키보드와 스크린 리더용 이름 확인
- [ ] 언어 품질 검수 완료
- [ ] `npm run lint`와 `npm run build` 통과

## 구현 전에 확정할 사항

국제화 코드 작업을 시작할 때 다음 항목을 명시적으로 확정한다.

1. 첫 번째로 공개할 번역 언어와 로케일 코드
2. 초기 공개 시 번역할 블로그 글의 범위
3. 번역 검수 담당자 또는 승인 방식
4. 원문 리비전 자동 검사를 빌드에 포함할지 별도 검사 명령으로 둘지

이 선택이 끝나기 전에도 한국어 사전 분리와 locale-safe 라우팅 기반은 구현할 수 있지만, 미완성 번역 언어를 공개 레지스트리에 등록하지 않는다.
